# P4：預收、墊付、實收與退款帳本

版本 20261108-6，資料庫遷移 4，HTTP 寫協議 2。此階段登記已發生的款項，不會發起支付或自動退款。活動、名額、應付帳單與實際款項各自獨立。

## 身分、權限與可見性

只有當前發起者能確認款項、登記實收／退款、沖銷及結清；協辦沒有財務權限。本人可以申報自己帳號的轉款、先付店家及訂金；代報管理人也可替自己管理的未綁定同行申報，操作人與款項歸屬分別保存。陌生訪問者不能替其他人申報。

沿用 P3 的活動內付款人 ID，不按暱稱合併。已確認的非報名付款人可在最終結算沿用同一 ID。每筆凍結稱呼、資金來源／去向、實際轉款／收款人、責任歸屬、金額、方式、時間、備註與原因。實際轉款人可與款項歸屬人不同，須填代付依據。

帳本、已確認金額及明細遵循活動公開／邀請權限。尚未確認、撤回或拒絕的申報原文及核對說明只對發起者、原申報者可見；公開活動異動紀錄只列申報操作，不洩漏申報原文。API 不回傳內部使用者 ID 或瀏覽器憑證。

轉交活動只轉交管理權，不挪動原代收資金或已付責任。新發起者可記錄實際移交資金；各持有人餘額必須對平。歸檔、取消後仍可處理帳款及更正。

## 款項與對帳

金額為正十進位字串，最多七位整數與兩位小數；內部一律整數分。零元結算可結清，但不新增零元款項。

| kind | 資金與責任效果 |
| --- | --- |
| collection | 參加者預收／實收：增加其淨投入及指定持有人的活動代收資金 |
| refund | 實際退還參加者：減少其淨投入，扣代收資金；也可由另一人先墊退，增加墊退人的淨投入 |
| reimbursement | 實際償還墊付：與退款相同的資金效果，分開標明用途；也支援另一人先墊還 |
| expense | 支付店家：個人直接支付時增加其淨投入；使用代收資金時扣持有人餘額；均增加店家淨消費 |
| merchant_refund | 關聯原支出或已抵消費訂金，減少店家淨消費；退至代收資金或原個人，分別增加持有款或減少個人淨投入 |
| deposit | 可退訂金／押金：增加待處理訂金，個人先付增加其淨投入，或扣活動代收資金；暫不計消費 |
| deposit_return | 關聯原訂金：減少未處理訂金，退至個人或活動代收資金 |
| deposit_apply | 關聯原訂金：轉入實際消費／損失，不產生新轉帳；須依據並核對 P3 費用 |
| credit_transfer | 更正已確認淨投入的歸屬，總額不變；須原因，不表示實際轉帳 |
| cash_transfer | 實際移交活動代收資金，不改任何人的應付或淨投入；須原因 |

個人待補 = 當前逐人結算中的應付 − 已確認淨投入。負數表示應退／待償還。尚未發布逐人結算時只列預收／墊付，不猜測應付或應退。同行的申報管理權不代表其費用屬於管理人；「我的待補」只計本人綁定帳號，其他人逐項列示。

P3 改額、改付款歸屬或移除某位付款人，不移動、刪除或重算原實收；舊付款人仍保留已確認投入，顯示應退／待償還，新付款人顯示待補。更正歸屬需獨立記錄並留原因。

已含在 600 元最終帳單中的 100 元訂金：先記 deposit 100，抵扣時記 deposit_apply 100，最後只記 expense 500，店家淨消費為 600。取消後退 80、扣 20 的訂金：記 deposit_return 80、deposit_apply 20，P3 另核對實際 20 元損失。P3 的店家退款／減免是費用變化，P4 的 merchant_refund 是實際資金返回，兩者不自動替對方入帳。

對所有有效款項，必須恆等：**全體淨投入 = 店家淨消費 + 尚未處理訂金／押金 + 活動代收資金餘額**。各人淨投入、各持有人代收餘額及關聯款項剩額不可為負。代收資金不足時可記錄真正的個人先付，或個人墊退／墊還，不虛構活動現金。對錯誤的歷史退款先沖銷相關記錄，再更正來源。

## 申報、確認與更正

申報只是一份待核對主張，不增加實收、墊付或店家支出。發起者核對後按申報原文確認；不符時填原因拒絕，重新申報或登記，不偷偷修改申報金額。原申報者可撤回待確認申報。已處理申報不能再次確認；已確認申報沖銷後仍保留確認決定，另明確顯示「入帳已沖銷」。每人最多 20 份待核對，全活動最多 500 份。

已確認款項不能 UPDATE／DELETE，只能追加 reversal 與更正的新款項。沖銷原收款若造成代收資金不足、或原支出已被退款／訂金已抵扣，會要求先處理後續關聯記錄。不能沖銷另一筆沖銷或結清檢查點。所有決定、沖銷、原因與原款項持續可查。

資料表：finance_reports、finance_report_actions、finance_entries，均有禁止 UPDATE／DELETE 的觸發器。同活動的外鍵及唯一來源申報／唯一沖銷目標防止跨活動引用、重複確認及重複沖銷。款項、審計、活動 revision、通知及請求結果在同一交易提交；任一步失敗全部回滾。

## 結清與重新開啟

活動結束不等於帳務結清。結清需要：已發布核對後的逐人結算、每位付款人差額為零、店家淨消費等於帳單、代收餘額為零、無待退／待抵訂金及無待核對申報。舊人均帳單不猜測個人欠款，須發起者明確轉換後才能逐人結清。

確認結清保存對應帳單版本及帳本序號。後續新增／沖銷款項、發布新帳單，重新進入待處理；舊結清記錄保留。發起者也可填原因主動重新開啟。單純新增待核對申報會暫停結清狀態；撤回／拒絕後，若沒有款項或帳單變動，原已結清檢查點仍適用。

## API 與手機流程

| 介面 | 用途 |
| --- | --- |
| GET /api/events/:id/finance | 對帳、持有款、訂金、申報及確認紀錄；各自每頁 100 條歷史，待核對申報另列 |
| GET /api/events/:id/finance?before=:seq | 更早的已確認紀錄 |
| GET /api/events/:id/finance?before_report=:seq | 更早的已處理申報，只回傳有權查看的內容 |
| POST /api/events/:id/finance/preview | 只讀核對，回傳正規化操作、預測資金餘額及 preview_token |
| POST /api/events/:id/finance | 同一輸入加 preview_token，提交操作 |

所有寫入與預覽要求協議 2、Idempotency-Key 和 base_revision。command 為 record／report／accept／reject／withdraw／reverse／close／reopen。record／report 另帶 id（16 hex）、transaction；申報決定帶 report_id；reverse 帶 entry_id；拒絕、沖銷及重新開啟須 reason。

transaction 共用 kind、amount、occurred_at（帶時區、不能在未來）、method（wechat／alipay／qq／cash／other）、note、reason。依類型填 payer_id、custodian_id、funding（payer／pool）、funder_id、actual_party_id、merchant、reference_id、from_id／to_id。最多可新增兩位 custom_parties: [{id:custom:<16 hex>,name}]，且必須用於本次實際款項；參加者申報不能建立其他人的款項身分。

一般參加者主要查看本人差額、申報並等核對；發起者看到待核對及對帳，進階設定收合。各操作先預覽再確認，表單改動立即使預覽失效。409 保留輸入，明確點「載入最新版（替換當前輸入）」才取代；不自動重送舊金額。相同請求重試不重複記帳、確認、退款或通知。結清後補錄入口收合，首頁依目前資金顯示待補、應退或已結清。

## 遷移與後續

遷移 4 只新增三張空表、索引、觸發器及遷移版本，所有舊活動、應付快照、人均帳單、圖片與歷史逐值保留。正式升級用隔離副本連續演練兩次，原服務使用者啟動遷移；不改 1Panel 或代理。正式資料不建立測試款項。

P5 接續草稿恢復、日常提醒、複製活動、導航及真實手機 QQ WebView 完整驗收。P6 等待 QQ 官方審核；此階段不依賴 QQ 或支付 API。
