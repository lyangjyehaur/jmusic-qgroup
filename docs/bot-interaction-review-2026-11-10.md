# Bot 交互審查與整合修改清單

日期：2026-11-10。對照版本：`16e4f9b`。

依據：網站操作手冊、活動／報名／身份／結算／帳務／恢復流程，以及 `qgroup_bot`、`bot_outbox`、`boardTodos()` 的現行實作。下文區分已確認缺陷與新增功能建議，供下一輪一起安排修改。

## 1. 整體判斷

目前 bot 的「查詢活動、通知重要變更、引導到網站處理」方向合理，能減少群友找連結與發起人重複解釋的工作。但七個指令尚未形成完整流程：選活動不明確、指令名稱與實際效果不一致、結算後的收退款與結清幾乎沒有接上，身份與權限也尚未完整落實。

建議交互分工：

- 群內：活動選擇、已允許同步的活動摘要、公開狀態與重要節點通知。
- 個人：報名狀態、安排確認、遞補、退出結果、本人／同行的付款責任及補退款。現在用登入後的網站；完成身份綁定及投遞能力驗證後，可增加私聊。
- 管理者：成團決定、退出／認領審批、出席核對、結算與帳務核對。入口可以從 bot 發起，實際權限仍按網站角色判斷。

群內發一句指令，與網站操作成功，是兩個不同階段。回覆必須清楚說明「開啟入口」「尚待確認」「已提交申請」「已完成」中的哪一種。

## 2. 上輪五項問題與本輪補充

| 編號 | 優先級 | 已確認問題 | 合併修改方向與驗收 |
| --- | --- | --- | --- |
| F01 | P1 | Bot 查詢繞過邀請制／草稿權限；主動廣播也未檢查可見性 | 查詢、排隊、發送、回呼都核對活動及群組範圍。未綁定身份不讀私人活動；草稿不進群。可見性在排隊後改變時也須停止不再適用的投遞 |
| F02 | P1 | dry-run 只阻擋 outbox，被動回覆仍會發送 | 所有發送路徑共用開關；模擬指令、按鈕、排程均不得呼叫發送 API |
| F03 | P2 | 改期／延長不更新排程，提醒人數是發布當下的舊值 | 提醒綁定安排版本及時間；到期重查有效性與人數。舊提醒作廢，新時間只排一次 |
| F04 | P2 | token／回應解析例外令訊息留在 sending、attempts 不增 | 每筆例外納入重試狀態，單筆失敗不阻斷同批其他訊息；提供退避、失敗原因及人工重送入口 |
| F05 | P2 | 無有效報名者時，安排變更不會廣播 | 根據安排版本變更建立一次通知，不依賴站內通知收件人數 |
| F06 | P2 | `/签到` 統計 `attendance='arrived'`，網站實際狀態為 present／late／left 等 | 新發現：隔離資料有 1 位 present，bot 回覆「已到場 0 人」。改用網站相同狀態定義；到場、遲到、早退、缺席、未核對分開顯示，未核對不等於缺席 |
| F07 | P2 | 繁體指令無法識別，未知指令又被當作活動查詢 | 新發現：`/活動 /名額 /待辦 /簽到 /結算 /幫助` 解析均為 None。接受簡繁別名，未知指令回說明；只有單純 @ 才走預設入口 |

F01–F05 已於上一輪隔離重現；F06–F07 本輪用暫存資料及解析器重現。F04 的「退避／人工重送」是修復時建議一起增加的能力。

## 3. 現有指令逐項調整

| 指令 | 現行行為／落差 | 建議交互 | 階段 |
| --- | --- | --- | --- |
| 單純 @、`/活動` | 直接挑與現在最接近的一場 scheduled／ongoing 活動；網站可同時有多場 | 先列本群可見且允許同步的活動，包含日期、階段與短碼。只有一場才直接回卡；多場讓使用者選，不要求記 ID | 第一批 |
| 指定活動 | ID 前綴查不到時，悄悄退回另一場；LIKE 還接受萬用字元 | 前綴限定合法字元；找不到或不唯一就明確提示。指定過的活動不能自動換場；過期按鈕亦適用 | 第一批 |
| `/名額` | 只有正式／候補／上限／最低人數，未說明能否報名；最低人數為 0 也照列 | 增加開放／暫停／截止、正式／候補／待確認人數。整組候補擋位時說明「有空位但須依隊列分配」；人數達標只表示可由發起人決定，不代表已成團 | 第一批 |
| `/待辦` | 只查一場、無角色身份；缺認領、成團、暫不同意、補退款與未結清等項目 | 群內使用「活動待辦摘要」及管理入口；個人／管理待辦於網站按角色顯示。未綁定時不回覆「你沒有待辦」；已結束但未結清活動也要能找到 | 近期摘要；個人化於綁定後 |
| `/簽到` | 名稱像能本人打卡，實際只回現場補錄入口；統計還有 F06 | 先以 `/出席` 為主，`/簽到` 作別名並明說尚未登記。區分已有名單的出席核對與未列名者的現場補錄；後者需報名＋出席權限 | 第一批 |
| `/結算` | 預設只挑尚未結束活動，反而漏掉最需要查帳的往期；只有版本／總額／人數 | 優先提供近期有帳單或待結算的候選活動，讓使用者確認。區分「未發布」「第 N 版已發布」「收退款核對中」「已結清」，並連到該活動結算或帳本 | 第一批 |
| `/我的` | 未識別使用者，仍顯示按時間挑選、未必與本人有關的一場活動及一般連結 | 未綁定時回「登入網站查看我的報名／同行／款項」入口，不暗示知道本人身份；綁定後按本人及代報管理關係列出活動，私聊或站內提供金額 | 近期入口；個人化於綁定後 |
| `/幫助` | 七個命令平鋪，未交代哪些只提供入口；簡繁未兼容 | 分「找活動／我要參加／活動管理／款項」，註明身份要求與效果。網站手冊補 bot 章節，更新現有「不會自動發 QQ」的過時敘述 | 第一批 |
| 訊息按鈕 | 回呼資料只有 `/名额` 等指令，未帶活動 ID，可能打開另一場；目前為選配 | 按鈕攜帶活動、動作及必要版本，接收時重查群組、身份、權限與狀態；回覆明確標示活動。官方面板／keyboard 格式、回呼確認方式及純文字退路另做實機驗收 | 第一批基礎；平台 UI 驗證後啟用 |

狀態名稱統一沿用網站用語，不直接輸出 `scheduled`、`confirmed` 等資料值。群組沒有瀏覽器語言，可先以既定群語言顯示、指令同時接受簡繁，不對使用者填寫的活動原文做全文轉換。

主選單建議先收斂為「活動／報名／我的／結算與款項／管理／幫助」六個入口。下文的 `/同行`、`/退出`、`/補報` 等是可支援的快捷方式或選完活動後的情境按鈕，不需要全部攤成一長串命令；原有名額、待辦與出席查詢繼續可用。管理入口也不授予管理權，只導向登入後有權操作的畫面。

| 情境 | 建議回覆示例 |
| --- | --- |
| 有兩場活動，使用者說 `/報名` | 「要參加哪一場？① 週六唱歌 ② 週日聚餐」→ 選定後「週六唱歌，目前開放報名。查看安排並報名：……。尚未替你占位，請以網站提交結果為準。」 |
| 活動換地點 | 「週六唱歌：第 3 版安排，地點已變更。原名額與原約定保留，請本人及代報管理人逐人核對。查看並確認：……」 |
| 使用者說 `/已付款` | 「請先選活動，再到站內申報實際轉帳；發起者核實後才計入已確認款項。開啟申報：……」 |

## 4. 可新增的流程：近期就能做

這一批不依賴 bot 與站內帳號綁定；敏感或需要授權的實際資料，由登入後的網站檢查。

| 編號 | 網站已有流程 | 建議 bot 入口／通知 | 重要行為 |
| --- | --- | --- | --- |
| N01 | 發起、草稿、複製上次活動 | `/發起` 開啟發起表單；`/再約` 先選可存取的舊活動，再到網站複製 | 新活動重填日期／截止；不帶舊名單、帳務、收款碼或協辦。私人草稿只在登入網站後查看 |
| N02 | 本人報名、同行／代報、待確認 | `/報名`、`/同行`、`/待確認` 選活動後進對應表單 | 顯示「開啟報名入口，尚未占位」。沿用網站預覽、整組排隊、部分候補確認與費用約定 |
| N03 | 退出、逾期退出申請 | `/退出` 開啟本人／可管理同行的報名入口 | 期限前撤銷、期限後申請需區分；申請送出不代表退出完成，也不代表退款 |
| N04 | 成團決定 | 人數達門檻或截止時，增加「待決定是否成團」管理入口 | 達標不自動成團，不足不自動取消。未綁定身份時不在群內公開發起者私人待辦 |
| N05 | 安排變更與逐人確認 | 群摘要寫明變更了時間／地點／費用／退出約定，以及安排版本；「查看並確認」進站內確認頁 | 接受或暫不同意由網站逐人確認；代報者須核對同行。未確認／不同意不自動退出或加費 |
| N06 | 暫停／恢復報名 | `/名額` 顯示目前開關；管理者在網站可選擇同步這次暫停／恢復 | 開始、截止、暫停分開；不在每次名額變化時自動刷群 |
| N07 | 地點及導航 | `/地點` 或活動卡提供集合地點與導航入口；可補 `/規則` 查費用與退出約定 | 只用該活動已允許分享的地點；導航由使用者點擊，無需定位授權。費用約定與最終帳單分開 |
| N08 | 補報邀請、報名認領 | `/補報`、`/認領` 說明流程並引導登入網站尋找相應管理入口 | 個別邀請／認領憑證只交指定人，不由 bot 發進整個群；不按同名合併或多占一個名額 |
| N09 | 出席核對、現場補錄 | `/出席` 查看允許公開的狀態摘要；「核對出席」「現場補錄」進網站 | 已報名者到場與新增臨時參加者分開。超額／越過候補須明確確認；已有帳單不得再補錄 |
| N10 | 預計結束、實際結束、延長 | 到預計結束時間提供「確認結束／延長」入口；實際結束後引導核對名單並發布結算 | 時間到不自動結束、不自動結算；優先提醒有處理權限的人，群內通知由發起者選擇 |
| N11 | 結算發布與更正 | 已有發布通知補上「首次／第 N 版更正」、更正項目類別及「查看最新帳單」 | 已付款不會被重置。舊卡標示其版本，打開網站顯示最新狀態及歷史；個別金額不作預設群廣播 |
| N12 | 實際轉帳後的款項申報 | `/已付款`、`/申報` 打開站內申報表；`/帳本` 打開帳本入口 | 回覆「請申報，待發起者核實」，不能回「已收到款」。沿用預覽、付款責任人、實際轉款人及審核流程 |
| N13 | 補款、退款、墊付回收 | `/款項` 引導到本人款項頁；帳單更正通知提示「請重新查看補退款」 | 訂金退回、店家減免與退款給參加者分開。網站只記帳，不執行轉帳 |
| N14 | 帳務結清、重新核對 | 接上 `finance_close`，由發起人選擇發一次收尾通知；帳單或帳本改動後顯示重新待核對 | README 已提及已結清收尾，但現行映射未實作。不能用活動結束、帳單發布或欠款合計為 0 代替完整結清 |
| N15 | 取消活動及保留帳務 | 現有取消通知補上退款／訂金處理入口；`/往期` 可找到取消、結束但未結清活動 | 取消不刪名單或帳務、不自動退款；已歸檔活動的帳單更正仍須可追蹤 |
| N16 | 協辦、轉交發起者 | `/協辦` 提供管理入口；轉交完成可選同步「管理已交接，詳見活動頁」 | 交接憑證只交指定人；協辦沒有帳務或轉授權限。轉交不等於代收資金已移交 |
| N17 | 不明提交結果、草稿與常見問題 | `/幫助` 提供「我是否報上／候補為何沒遞補／轉帳後怎麼辦／提交斷線」入口 | 引導原瀏覽器「待確認操作」查原結果。bot 不能讀取另一瀏覽器的本機草稿或原請求憑證，不能代猜成功或要求重填一筆 |

入口需要網站支援指定畫面。現在首頁啟動只認活動及既有邀請／帳號類參數；新增 `action=join/conditions/finance` 等屬待實作功能，不能只把參數拼進連結就宣稱能定位表單。登入返回後還需保留活動與目標動作，再重新檢查身份及權限；GET 連結只導覽，不直接寫資料。

## 5. 完成身份綁定後，可再加入的個人流程

| 編號 | 新增交互 | 與網站一致的規則 |
| --- | --- | --- |
| B01 | `/綁定`、`/解除綁定`、網站查看已連接 bot 身份 | 驗證站內登入者與發訊 QQ 使用者均為本人；不能按暱稱、QQ OAuth subject 或空的 union_openid 猜測對應。按 bot app 及平台身份作用域保存映射；解除、註銷與切換帳號須撤銷對應能力 |
| B02 | `/我的` 查本人報名、同行、候補與安排確認 | 分清本人 user_id、代報 manager_id、同行及付款責任；認領後按新的管理權展示，舊付款責任依網站保留 |
| B03 | 遞補、退出決定、認領結果、安排確認的個人提醒 | 只送當前有權接收者；不公開申請原因。現有 private outbox 沒有保存站內收件人，需先補 user_id／接收關係及可追蹤的投遞資料，不能只填 target 就認為完成 |
| B04 | 發起者／協辦的個人待辦摘要 | 按 owner／schedule／roster／attendance 角色產生；協辦不取得財務待辦內容。轉交或撤銷權限後，舊訊息按鈕仍需重新驗權 |
| B05 | 私聊查看應付、已確認投入、待補、應退、墊付待收回 | 複用 `finance.summary()` 的本人付款鍵及責任關係；顯示帳單版本與核對狀態。不能把「已申報」算作已付款；不把別人的責任攤到發指令者 |
| B06 | 確認過活動與安排後，bot 直接做本人報名／退出申請 | 顯示最新約定、正式或候補預覽、影響與最後確認；沿用版本檢查與請求去重。若資料變動要求重看，不把衝突請求自動改版本再送 |
| B07 | 直接回覆「接受新版安排」或「暫不同意」 | 綁定活動、安排版本及指定參加者；本人與同行分開確認，不能用單一句「接受」替全部同行接受。暫不同意的原因走私聊／站內 |
| B08 | 個人款項申報、發起人核對提醒 | 優先維持站內表單；若之後加入 bot 表單，完整保留申報、預覽、審核及追加歷史，不以群聊「已轉」直接確認入帳 |
| B09 | 收款碼與帳單的授權查詢 | 先交付站內最新版本入口；之後才驗證私聊／官方媒體 API。只讀該帳單已發布的圖片，不讀發起者私人碼庫；更換圖片須跟帳單版本一致 |

綁定可以研究獨立的雙端驗證，不必假設一定能從 QQ 互聯取得與 bot 相同的識別碼；這也不會替尚未完成 QQ 網站登入的人建立登入能力。優先驗證私聊或受控雙端流程，短效、一次性、防重放、防搶綁；群內公開的一條持有者連結不足以證明身份。

身份綁定與私聊投遞是兩項不同前置條件。即使已能識別本人，平台不允許該次私聊時仍應提供站內入口，不能降級把個人金額發到群內。

## 6. 待辦與通知應如何對齊網站

目前 `/待辦` 不是網站 `boardTodos()` 的完整映射。網站待辦在前端根據已驗權的活動視圖計算；bot 目前直接查資料庫計數，沒有使用者與角色上下文。

| 網站已有待辦 | Bot 現況 | 建議呈現 |
| --- | --- | --- |
| 確認變更後安排 | 只有 pending 計數，未處理 declined；無本人／同行範圍 | 群內提醒存在新版；本人／代報管理人於站內或私聊逐人處理 |
| 核對報名認領 | 缺 | 有權管理人的待辦與認領頁入口 |
| 處理退出申請 | 有總數，無角色範圍 | 有報名管理權的人處理；私人原因不進群 |
| 決定是否成團 | 缺 | 發起人看到達標／截止及成團決定入口 |
| 確認結束／延長 | 有部分計算 | 使用活動目前時區、時長及階段；修改安排後立即更新 |
| 核對並發布結算 | 有分支，但預設選活動排除 ended／cancelled | 往期與取消活動均可列入；僅有權發起人執行 |
| 款項申報待核對 | 有總數，未對齊角色 | 發起人看待審；申報者看自己的申報；不給協辦財務權限 |
| 我的待補／退款／墊付待收回 | 缺 | 登入網站或綁定後私聊，按付款責任計算 |
| 核對收退款與結清 | 缺 | 發起人看完整結清阻礙；群內只送選定的進度或結清結果 |

建議抽出有 viewer／角色上下文的共用查詢與待辦規則，讓網站與 bot 對同一份測試案例得到一致結果。不能宣稱直接複用前端函式，卻另外用幾條 SQL 重寫不完整版本。通知已讀只改讀取狀態，不清除仍未完成的待辦。

## 7. 群同步與發送控制

1. 保留環境總開關，網站增加活動是否同步到主要群的選項；發布、重要變更、取消、結算更正、結清等操作可以預覽並選擇同步本次結果。由有該操作權限的人決定，群組路由則由受控設定決定。
2. 先支援部署設定的主要群並限制入站群組；多群需求明確後再增加活動與群的關聯。不能因 bot 被加入另一群，就自動把整站活動帶過去。
3. 邀請制活動預設不自動進群；若要分享，另設清楚的受眾與授權流程。普通活動 ID 不授予查看權；不要為了讓卡片可點，自動附上補報、認領、交接或設備授權憑證。
4. 不逐筆廣播報名、退出申請與金流。群查詢提供目前摘要，個人變動給本人或對應管理者；提醒針對未完成狀態產生，完成後停止。
5. 文案預覽包括標題、地點、注意事項及原因。這些是使用者原文，可能包含姓名或私人資訊；不能只因程式沒讀 nickname 欄位，就保證已「去識別化」。
6. 發布／變更／結算採版本化的事實快照；排程提醒在到期時核對目前狀態並產生適用內容，另保存實際送出快照。不要為更新提醒而覆寫已發布的歷史 payload。
7. 去重使用活動、業務動作／版本及目標，不能只靠文字完全相同。管理者明確要求重送時記錄新投遞意圖，避免同一文字被永久吞掉；不以固定每場訊息數取代「是否有全群需要知道的事」判斷。
8. 網站顯示「未同步／待送／模擬／已送／失敗／已作廢」及時間；已送只表示平台接受，不代表群友已讀。dry-run 不應在介面冒充已真實送達。可手動重送可重試的通知，不能重做原業務操作。
9. 發送前再次核對群組、接收者、活動可見性與提醒狀態，避免排隊期間轉交、撤權、取消或隱私設定改變後仍送出舊內容。

維運配套：修改 `/etc/qgroup/*.env` 後需要以 `docker compose up -d` 重建受影響服務以載入新環境；單純 `docker compose restart bot` 不會更新容器環境變數。Bot 的健康狀態應涵蓋最近連線／心跳與 outbox 輪詢成功時間，不能只看容器仍在 running。

## 9. 合併修改的驗收案例

- 同時有兩場新活動、一場已結束待結算及一場取消待退款，指令與舊卡按鈕都不會選錯場。
- 指定 ID 不存在或前綴不唯一時明確提示；普通 @、未知指令、簡繁指令的結果各自正確。
- 私人草稿、邀請活動、未授權群、未授權私聊及失效按鈕均不能繞過存取限制；排隊後修改可見性亦有效。
- dry-run 下觸發普通指令、面板／keyboard、主動通知與定時提醒，全部零發送；網站顯示模擬而非已送達。
- 額滿、整組候補擋位、待確認、暫停及截止狀態，bot 說明與網站預覽一致，不把空位當作報名保證。
- 活動無有效報名者仍能同步重要變更；有代報同行時，確認本人不會替同行全部接受。
- 改期、延長、取消、歸檔後，舊提醒不發；新提醒用最新人數及目前有效版本。
- 有到場、遲到、早退、缺席、未核對的名單時，出席摘要與網站一致；文字不宣稱已替本人完成簽到。
- 部分人已付款後更正帳單，已確認款項保留，待補／應退依最新版重算；不把申報當作確認入帳。
- 取消且訂金部分退回時，bot 不宣稱已全額退款；活動結束或已收齊款項均不直接宣稱結清。
- 認領、轉交或撤銷協辦後，個人待辦、按鈕權限及未送通知的接收者更新，原付款責任按網站規則保留。
- token 失敗、非 JSON 回應、頻控及單筆例外不阻斷整批；有重試退避、上限及可查原因。超時後重送不重做業務操作。
- 直接操作階段測試重複事件、衝突、斷線與恢復：只產生一次報名／申請／帳務紀錄，且回覆區分成功、未提交及結果未知。
- 登入返回仍定位原活動與動作；本機草稿與原請求查回留在有資料的瀏覽器，不因 bot 入口另建重複操作。
