# Web／bot 發布與相容性規則

## 目標與目前狀態

本文件是 web／bot 發布範圍、相容性驗證與版本組合紀錄的共同依據。目標是保證已驗證的版本組合；web 和 bot 可以使用不同 commit 或映像，純單邊修改不要求另一邊重新建置或重啟。

保留的舊版 `compose.yaml` 讓兩個服務共用 `qgroup:${QGROUP_TAG:-local}`；目前正式統一版使用 `deploy/unified-compose.yaml` 分別固定 web／bot 映像。API 或 bot 運行程式改動須建置核准來源映像；純文件修改不建置、不部署。

獨立前端發布使用 `deploy/frontend-compose.yaml` 唯讀掛載前端父目錄；啟用後純 UI 更新只建置與切換靜態檔案包，不建置映像、不重啟 API 或 bot。由現有 API 提供同源靜態 HTTP，保留安全標頭與語言規則。首次啟用仍須更新 web 映像一次，操作與相容性限制見[前端獨立發布](frontend-release.md)。

目前已有 release manifest 與明確映像引用；`deploy/check_release_source.py` 提供來源檢查，前端工具另核對檔案摘要、後端輸入指紋及指定 API 版本。完整 CI 自動發布與語意相容性證明尚未實作，不能把人工驗證或指紋相同當成所有功能必然相容。正式環境路徑、備份與操作方式以 [README 部署與保全](../README.md#server2-部署与保全) 為準。

## 分支與發布來源

1. 功能分支完成測試後，先整合並推送 `main`。正式新版本只能取自遠端 `origin/main` 歷史內的明確提交；不要求每次都部署 main 最新提交，但禁止發布尚未合入 main 的功能提交。
2. 發布前在乾淨的 Git 工作目錄執行 `python3 deploy/check_release_source.py --commit <完整 SHA>`。工具重新取得遠端 main、驗證提交存在於其歷史，並拒絕未提交或未追蹤檔案；失敗就停止。工具只輸出核准的完整 SHA，不上傳、不建置、不部署。
3. 使用檢查通過的 SHA 執行 `git archive`，在新的乾淨目錄解包、建置一次，再依既有保全與相容性流程發布。禁止使用任意 `HEAD`、工作目錄覆蓋檔案或在正式機直接 `git pull` 後建置；Git 分支名稱不是部署版本識別。
4. 回退以已保存的歷史映像或不可變前端檔案包與經驗證的版本組合為準；重建歷史版本時仍需驗證來源在遠端 main 歷史內，並重新確認資料相容性。前端、API、bot 可以各自使用 main 的不同提交，不為同版而重啟另一服務。
5. `main` 更新與正式部署分開。已整合分支停止開發，新工作從最新 main 起步；舊草稿獨立保留，確認哪些差異仍有需要後才整合。

這是專案操作規則與可手動執行的來源檢查，目前沒有伺服器端分支保護或不可繞過的自動發布閘門。不得宣稱所有手動 Docker 操作已受到限制。

## 發布範圍判定

每次變更在工作交付或發布紀錄中標明 `web`、`bot`、`both` 或 `none`，並說明判斷理由。修改路徑只是線索，實際依賴與資料契約才是判斷依據。

`web` 範圍須另註明 `frontend`、`api` 或兩者。純 `frontend` 發布將下列映像建置／版本檢查對應為不可變靜態產物、完整來源 SHA、PWA build ID 和 manifest／逐檔摘要；仍須驗證實際運行的 API／bot 組合，記錄兩容器未變。涉及 API、共用契約或依賴修改時，不得套用純前端發布來跳過後端驗證。

| 變更類型 | 發布範圍原則 | 驗證重點 |
| --- | --- | --- |
| 純部署文件、開發說明，沒有運行產物變更 | `none` | 文件連結與指令是否符合現況 |
| 網頁樣式、文字、前端互動，沒有改動 bot 依賴的入口或契約 | `web` | 相關前端測試、生成產物與網站健康 |
| web 後端修改，保持 bot 使用的資料及共用行為相容 | `web` | 相關後端測試及新版 web 與線上 bot 的配合 |
| bot 指令、QQ 連線或投遞修改，保持現有資料及網頁入口相容 | `bot` | bot 測試及新版 bot 與線上 web 的配合 |
| 共用核心、schema、outbox 格式、設定語意、跨服務業務規則或入口 | 先按 `both` 評估 | 新舊組合、資料遷移、待送消息及回退相容性；證明只有單邊受影響後才可縮小範圍 |
| 不相容的跨服務變更，或無法證明可單邊發布 | `both` | 停機／切換順序、遷移與成套驗收 |

特別注意：bot 會匯入 `qgroup_core` 並讀取共用 SQLite；web 產生 outbox，bot 消費及更新投遞狀態。`server.py` 或 `public/` 的修改也可能影響 bot，因此「只改某個目錄」不能直接等同「另一服務不受影響」。

修改網頁或系統文案時，仍須依 README 重新產生所需手冊與簡繁產物。生成檔如 `qgroup_core/locales.json` 的影響也要檢查，不得直接修改生成檔或漏發相關產物。

## 單邊發布要求

1. 取得兩個服務目前實際運行的映像 ID、可追溯的來源 commit，以及目前資料庫遷移狀態。若無法確認未更新服務的實際版本，先補齊資訊，不能猜測相容。
2. 從明確的來源 commit 建置一次，使用不覆寫的版本標籤並記錄 image ID；透過 registry 發布時記錄 digest。不能只憑 `local`、`latest` 或其他標籤判斷程式版本。
3. 先完成受影響測試，再驗證「新版目標服務＋目前線上未更新服務」的版本組合；只跑最新版全套單元測試不能取代混合版本驗證。
4. 驗證使用隔離資料庫及受控／模擬的 QQ 投遞，不對正式資料或真實群聊做破壞性驗收。資料庫遷移使用 `deploy/verify_migration.py` 在備份副本演練。
5. 發布時只更新選定服務。完成後確認目標服務等於預期 image ID、另一服務仍為原 image ID，並檢查兩邊健康及相關業務流程；兩邊不必彼此同版。
6. 記錄實際結果；失敗不能記成發布成功。先依預定方案處理失敗服務，確認版本組合仍相容，再決定是否恢復原映像。

保留的舊版 Compose 共用 `QGROUP_TAG`，無法表達不同版本，不得用它啟動目前正式服務。統一版與前端 override 已分別表達固定映像與獨立靜態目錄；仍須保留並記錄未更新服務的原版本，在整組啟動、重建或主機恢復前核對。

## 共用契約與成套發布

- 完整測試優先在本機或獨立 CI 執行，不在正式主機並行執行完整測試。可匯出已建置映像到本機驗證，核對 image ID，無須在正式機重建。
- 正式主機僅執行必要的備份、隔離遷移及輕量驗收；先確認可用資源，為驗證容器設定明確的記憶體、禁止額外 swap、CPU、PID 與執行時間上限，依序執行。資料庫／網路隔離不代表 CPU／記憶體隔離。資源不足時停止驗證並移到其他環境，不以正式服務的可用性換取測試結果。

- schema 的新增先保留仍在線上的程式所需欄位與語意；刪除、重新命名或改變既有欄位含義前，先確認舊版本不再運行及回退需求。
- outbox 修改須處理升級前已存在的待送消息，以及過渡期可能產生的新消息。若需要不相容格式，先設計明確的格式版本與不支援時的處理方式；目前不預設已有協議版本檢查。
- 共用設定的預設值與解讀方式也屬契約，不能只比較環境變數名稱是否相同。
- 成套發布不等於原子切換。若新舊版不能並行，預先準備映像與備份，進入維護窗後先停 bot、再停 web，完成必要遷移並驗證，再啟動新版 web、最後啟動新版 bot。失敗依事先確認的恢復方案處理。
- 回退以經驗證的版本組合為準：單邊回退若仍相容，就只回退該服務；不相容時成套處理。程式回退前確認舊版能使用現有 schema 及資料；發布後已有新寫入，不得直接覆蓋成舊資料庫。

## 發布紀錄

每次正式發布在 `docs/releases/` 新增或更新相應紀錄，保留以下資訊，不記錄密鑰、環境檔原文、個人資料或正式資料庫內容：

- 發布識別、時間及發布範圍（`web`／`bot`／`both`）。
- 發布前後兩個服務的來源 commit、映像引用及實際 image ID／digest；未更新服務也必須記錄。
- 獨立前端的來源 commit、PWA build ID、manifest 摘要、發布目錄與相容 API commit；前端 SHA 不冒用 `/api/v2/version` 的 API SHA。
- 資料庫遷移前後狀態、outbox／設定契約影響，以及是否允許新舊版並行。
- 驗證過的版本組合、執行的測試、結果及尚未完成的驗收；不得把模擬投遞記成真實 QQ 驗收。
- 回退目標版本組合、資料相容性限制及必要的恢復步驟。

尚未發布的設計或範例必須明確標示，不得填入虛構的正式 image ID 或發布成功結果。

## 後續自動化的落點

以下為待實作項目，不是現有能力：

- 保留的舊版 `compose.yaml` 尚未拆分映像；目前正式服務已使用 `deploy/unified-compose.yaml` 的獨立固定引用。
- Release manifest：將既有人工維護清單接入工具驗證與 Compose，記錄兩個服務各自固定的映像及來源版本；單邊發布只改相應服務的引用。
- `deploy/` 的發布工具：取得部署鎖、驗證 manifest、執行對應測試與遷移演練、只更新指定服務、核對兩個實際版本並記錄結果。
- CI：檢查變更影響與要求的驗證證據；路徑判斷僅提供建議，不能單獨作為相容性保證。
- 運行狀態：從映像內的建置資訊回報版本，再與 manifest 比對；健康與版本都通過才算發布完成。
