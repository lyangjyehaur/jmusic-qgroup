# Lovable 統一網站原型 Prompt

發布範圍：`none`。下方區塊可直接貼到 Lovable；原型使用虛構資料，不接正式服務。本文件不修改現有產品或發布流程。

```text
請為「群聚」設計並實作一個全新的、可以實際點擊操作的 React + TypeScript + TSX 網站原型。

這是一個以日本音樂為共同興趣的社群工具，整合約唱／聚會活動、報名與同行、分房與費用、個人音樂成分、同好匹配和 QQ bot。請把它視為同一個產品來設計，讓活動與音樂偏好自然串接。使用者需要找到活動、報名、了解自己的狀態、選擇喜歡的音樂，以及找到同好。

一、設計方向

請採用現代、克制、有辨識度的日式音樂社群設計：暖白背景、炭黑文字、深苔綠主色，細緻的灰色分隔線。用字體比例、網格、留白、對齊和少量色彩建立層次。可以使用少量有辨識作用的頭像與音樂分類圖形。

不必沿用 Yahha UI。請建立新的設計語言；避免手繪紙片、滿版粉色、每個按鈕都膠囊化、過度圓角、大面積漸層與玻璃效果。不要直接把元件庫的預設元件往頁面上堆。

正文以 14–16px 為主，次要資訊仍須清楚可讀。採用 8px 間距系統，相關操作間距約 8–16px，卡片內距約 20–24px，主要區塊間距約 24–32px。依內容調整，不要讓全部區塊有同樣的重量。卡片只用於需要分組的內容，不要每段文字都包卡片。

所有介面文案使用繁體中文。不要加入標語、歡迎段落、品牌理念、裝飾性英文副標、重複頁面介紹或行銷式 hero。保留頁名、欄位、操作、實際資料，以及有用途的狀態、驗證、錯誤、權限、風險與操作提示；提示簡短並靠近相關操作。版面不能靠新增文字來填滿。

二、統一導航與響應式佈局

主導航只有「活動、音樂、同好、我的」。桌面採用精簡側欄，主內容有清楚的頁首與操作區；手機使用固定底部 dock，保留文字標籤、選中狀態與至少 44px 觸控區域。全站搜尋、收件匣與帳號選單有固定位置。

手機的 dock 必須避開安全區，保存列放在 dock 上方；內容、輸入欄、視窗底部操作不能被遮住。請實際處理 360、390、768、1280px，不能只將桌面版縮小。長日文名稱、多人名單、費用表和篩選控制項都必須可讀，不能造成整頁橫向捲動。

全站沿用同一個帳號、稱呼、成分、未讀狀態與導航。活動名單可以查看該人的音樂成分，從活動進入分房或編輯成分後可以回到原活動。收件匣項目直接回到對應活動和操作。

三、請完整設計這些核心畫面與動線

1. 活動列表 /activities
提供可掃讀的活動列表，清楚呈現名稱、日期時間、地點、目前人數／上限、生命週期與本人報名狀態。可切換所有活動、我的活動和往期，提供搜尋與狀態篩選。主要操作叫「新增活動」。統計只是輔助，不要佔據第一屏的大部分高度。

2. 新增活動 /activities/new
表單保留名稱、類別、地點、說明、開始時間、持續時間、時區、報名／退出期限、容量、最低成團人數、費用規則、可見性與 QQ 群同步。分成清楚的表單區塊，常用欄位優先，進階欄位按需展開。底部提供「保存草稿」與「發布活動」，使用者可直接選擇發布，不必先手動保存再找另一個頁面。發布前核對安排與費用，明確提示發起者會加入報名；草稿不開放報名或發送群通知。複製活動只帶入安排，不複製人員、款項或歷史。

3. 活動詳情 /activities/:id
以活動為操作中心：先看到時間、地點、費用規則、報名狀態和本人下一步，再看到名單、分房與費用。未報名顯示「本人報名」，已報名顯示目前狀態和「管理本人報名」；同行／代報名獨立，不能混成同一個按鈕。

從詳情開啟報名或管理操作時，保留活動背景與原位置，使用可直接定址的對話框；手機可使用全螢幕操作視窗。關閉後回到原活動。涉及大量表格或多步編輯時可以使用子頁，但保留活動名稱與明確返回入口。不要讓使用者在幾個看似無關的頁面反覆跳轉。

報名包含本人、同行／代報、個別／整組候補、待確認、退出與逾期退出申請。提交前展示逐人分配與費用確認。名單上的操作直接帶入對應人員，支援出席、遲到、早退、缺席、現場補錄與認領。普通成員與發起者看到的管理操作要符合權限。成功後更新活動與名單；有未保存修改或結果未知時保留原稿並提供明確恢復操作。

活動亦保留公開／邀請可見、分享、地圖導航、安排版本與重新確認、協辦與結算人邀請、發起者交接、暫停／恢復報名、開始／結束／延長、取消／歸檔和操作歷史。進階操作合理收納，不要平鋪一整排按鈕。

4. 音樂 /music 與我的成分 /me/music
音樂頁以搜尋和探索詞條為主：提供名稱、別名、拼音／首字母搜尋，類型與分類篩選，熱門排行／完整詞庫，以及獨立的領域／細分清單和氣泡視圖。每個詞條清楚呈現名稱、分類、選用人數與是否已選；點擊可查看詳情、選取者、相關詞條和編輯入口。統計保留成分數、詞條數與近 24 小時變化，但保持輔助地位。

個人成分最多選 5 個領域、15 個細分，合計 20 個；細分有「本命、常聽、聽過一些、只聽過幾首」四檔。桌面有清楚的個人選擇區，手機有選擇摘要與保存操作。搜尋、切換詞庫、查看詞條和返回成分編輯時，選擇、熟悉度與未保存原稿都要保留，不要每個頁面生成一份不同的選擇。

保留詞條建立／修改／刪除、我的詞條、個人成分資料、固定成分 ID、聯絡 QQ、名稱／留言／性別可見性、找回舊成分、分享圖片與音樂趨勢入口。

5. 同好 /people、成分卡與比較
同好頁同時有查詢和推薦：透過固定成分 ID／聯絡 QQ 查詢或比較，並提供「共同項／冷門優先」與「我的熟悉度優先」排序。推薦先展示前三位，其餘同好可以展開，資料較少的同好另有分組。

同好卡優先展示名稱、匹配度和共同喜好。用有節奏的卡片、標籤與字體層次呈現內容；共同詞條的雙方熟悉度要容易比較。嚴格重合、領域／細分重合、共同本命、冷門詞條與完整排序規則可展開查看，不能為了美感刪除。授權可見的留言、性別和聯絡資料按權限顯示。名稱、成分 ID、聯絡 QQ 可複製；查看成分卡、比較、查看詞條後可返回原推薦與排序。

比較頁展示共同、只有我選和只有對方選的詞條，以及雙方完整成分。另保留同好圈子、找搭子與歷史、音樂趨勢和自由分房的入口與合理畫面，不要把它們做成互不相關的另一個網站。

6. 分房、時間投票、結算與帳本
時間投票支援日期／精確時段、可以／可能／不行、統計、截止、定案與建立活動；投票不等於報名。

分房包含正式包間安排，以及依音樂成分進行的自由試算：選取人員、房數／容量／自訂人數、手動移房、重新計分和分享圖片。試算結果與正式分房清楚區分，採用為正式安排時須預覽及權限確認。

費用區分應付帳單與實際款項。提供 AA／半 A／免共同費、費用項目與指定分攤、多人合付／代付、憑證和收款碼、包間消費、逐人應付與版本歷史。帳本保留付款申報與核對、收款、退款、墊付與償還、訂金／押金、轉款、更正及沖銷、待補／應退、結清與重新開啟。不要把「指定付款人」「申報已付」或「展示收款碼」當成真實付款完成。手機先展示本人摘要，再按需展開明細。

7. 我的 /me、收件匣與後台
我的頁提供本人活動、活動草稿、成分、詞條、收款碼、站內稱呼、QQ 綁定／重新授權、多帳號切換、裝置管理、外觀與語言、隱私同意、成分刪除及帳號註銷。成分刪除與帳號註銷是不同操作。收件匣包含通知、未讀與待辦，已讀不代表待辦完成。

後台有清楚入口，保留成員／權限、活動與投票管理、詞條／成分管理、找搭子管理、壁紙、隱私審核、備份與恢復紀錄，以及 bot 群政策、模板、提醒與勿擾、投遞紀錄和診斷。後台可使用更緊湊的表格和工作區，但沿用同一套設計。

四、QQ bot 的設計邊界

bot 仍支援活動、報名入口、名額、我的、待辦、出席、同行、退出、發起／再約、安排確認、地點、規則、結算、款項／帳本、申報、補報、認領、協辦、往期與縮寫等既有功能和別名。原型不需實作 QQ 通訊，但要設計群同步設定、通知內容預覽、投遞狀態、錯誤與重試，以及 bot 連結開啟對應網頁操作的流程。

所有舊活動、邀請、投票、認領與 bot 深連結都需要有對應目的地，不能因導航重整而丟失。bot 的連線恢復、投遞與既有指令屬後續系統保留要求；不要在原型宣稱已驗證或已連線。原型中的群同步和付款使用模擬狀態，不發送真實訊息或操作真實款項。

五、原型實作與資料

使用 React、TypeScript、TSX 和真正路由，以共用元件、設計 token 和獨立 mock service 實作。先完成前端原型，不啟用 Lovable Cloud／Supabase 或連接正式後端。型別、資料與 UI 分離，方便之後接既有 API；權限判定與狀態切換要有一致的模型。

請用虛構使用者與合理示例資料，包括不同活動狀態、正式／候補／待確認／逾期退出、長中日文名稱、沒有成分的會員、少量成分的同好、通知錯誤與待核對款項。可以按約 50 位會員、150 個詞條的規模設計資訊密度。不要使用真實 QQ、token、憑證或正式資料庫。

搜尋、篩選、頁籤、展開、查看詳情、報名預覽／提交、保存成分、排序、比較、分房調整、帳單預覽和通知跳轉需要真的可以操作；mock 修改在重新整理後保留。重要表單有未保存提示、失敗重試和恢復流程。不要只畫靜態圖片，或放沒有反應的主要按鈕。

六、交付優先順序

先完整完成「活動列表 → 新增／發布 → 活動詳情 → 本人與同行報名」及「音樂搜尋 → 詞條詳情 → 成分選擇／保存 → 同好推薦 → 成分比較」兩條動線。這些核心頁面都要有完整桌面與手機版。其他功能須在資訊架構中保留位置，提供代表性操作畫面；尚未完成的原型流程另列清單，不能用假成功掩蓋。

直接開始建立原型，並自行選擇與上述方向一致的字體、色彩與細節。交付時列出實際完成的頁面與可演示動線。請把設計判斷落實在畫面中：主次、留白、對齊、內容密度與操作位置都需要經過規劃。
```
