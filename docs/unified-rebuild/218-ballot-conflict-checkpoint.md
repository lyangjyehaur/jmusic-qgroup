# 第 218 批：逐人投票填答衝突保護

發布範圍 `web`：修改新版網站 API／React 填答表單與契約，沒有修改 schema、outbox、共用 Python 核心或 bot 執行程式。單邊正式切換仍須驗證新版候選與實際線上 bot 的組合；本批沒有合併 main 或部署。

同帳號兩個填答頁使用相同安排 revision 時，後送的舊答案原本仍可覆蓋另一頁的新答案。已在隔離 API 重現；修正前的四個競態案例有兩個失敗。既有定案票數版本只保護管理操作，無法防止逐人改票衝突。

API 現在提供目前帳號的填答摘要 token；新填答同時檢查原 token 與安排 revision。摘要包含該人的原票、時間與同投票的操作回執，涵蓋同秒內改票及答案改回原值；別人的票不使本人的表單失效。檢查與寫入在同一立即交易，拒絕後整庫不變，訪客不取得 token。

舊版原生 payload 仍可查回已提交的原 UUID／完整內容回執；目前登入與權限先檢查，再查回執，不重放舊票。未提交且缺 token 的原稿必須明確核對新版。原 Python 請求格式仍嚴格拒絕新版 token 欄位，沿用原 inspection／retry proof，不改舊 body 或簽章。

React 保留原 choices 與 token；409 確認拒絕後才持久化解除待查操作，未知結果繼續保留同 UUID／內容。舊原稿恢復不丟選擇、不自動送出；「核對最新候選，保留選擇」明確讀取最新版後才可再送。新增文案只提示相關衝突與處理方式。HTTP 身分邊界重新審核並更新五個變更來源摘要，錯誤顯示由既有生成工具產生。
