# 第八十批實作：舊包間／收支原稿轉換與款項來源核對

日期：2026-11-18（Asia/Taipei）。分支 `codex/unified-rebuild`。變更範圍 **`web`**，實際發布範圍 **`none`**。只使用隔離 fixture 資料庫、瀏覽器 context 與 mock QQ；未合入 main、未部署，未操作正式 bot、憑證、群設定或待送工作。

## 真正帶入新版表單

`舊看板本機紀錄` 現在能檢查並明確採用原 `rooms`、`finance` 草稿，支援原 fields 格式及 `{react:1,value,revision}` 格式。帶入的是實際 TSX 包間／收支編輯器使用的持久草稿，保留原房間 ID、名稱、人員、付款人、原款項 ID、非建立操作的固定目標、金額、備註、依據與版本；不送出原請求或另產生款項編號。

原來源及保全快照仍可查／下載。未知或重複欄位、缺業務欄位、key／操作／目標不一致、無效固定款項 ID 會拒絕轉換，不能套用目前預設值。原非登記操作的 reason-only fields 稿仍可帶入；不要求不存在的款項表單欄位。

帶入後必須先核對最新名冊／帳本，再重新確認或預覽。核對只更新基準，保留輸入。包間付款人目前不可選時保留原選項並提示核對；本版已移除的人員保留到使用者明確取消勾選，不再要求刪掉整個房間才能調整。既有「已發布結算不能再更改預分包間」規則保持；這種來源只能保全，實際包間須在結算中更正。

## 原款項狀態及停用欄位

新增受 session、scope、CSRF、origin、目前活動存取與權限限制的只讀 `/api/v2/activities/:id/finance/origin`。它按原固定 ID 查詢，不新增 request result、帳本、通知或 bot 工作，也不返回款項原文或私人內容。登記須有結算管理權；申報只供本人或管理者核對；缺失申報也須有目前申報資格。未發布／刪除活動、不同活動或操作佔用相同 ID 不能當成「尚未建立」。

已確認申報與其帳本項目共用原 ID，按原資料關係辨識為 accepted，避免誤判為其他操作的碰撞。pending／accepted／rejected／withdrawn 均可唯讀核對。已有登記或申報的後續草稿只讀保留，不能另建；轉換確認前再查一次原結果，另一分頁已提交時要求重新檢查。

原自訂人員選項完整保存於本機，產生預覽、提交與 pending 比對時只帶入該款項類型及資金來源實際使用的人員。後端維持每次最多新增兩位及本人申報不能新增其他人員的原限制；沒有放寬帳本契約。

依據沿用原兩種表單的送出語意：需要原因的操作取原 reason；React 其他款項取原 actual_reason；fields 格式非代付類型停用的 actual_reason 不轉成本次依據。原未送出的 reason／actual_reason 仍存於來源及提示。訂金抵扣與歸屬更正原表單停用的 method，沿用原後端的 other，同時保全原選項。本人支付店家／訂金申報按原 personal funding 語意帶入，遇到來源中殘留的 pool 選項會明確提示，不能當成活動代收資金申報。

原款項 wall time 沒有保存活動時區，提供原 IANA 時區輸入；不猜目前裝置或目前活動的時區。沒有時區、DST 歧義或未完成時間，保留原值與原因，目的時間留空需核對補齊。轉換預覽將原時區時間與目的台北 UTC+08:00 時間並列；保存的 UTC 時刻不變。

## 目的提交與隔離

沿用 strict IndexedDB transaction／CAS：先提交目的草稿，再保存來源映射；目的已有不同稿須明確保全，pending 一律禁止覆寫。目的成功而映射中止時不宣稱採用成功，可精確重試原 staged raw。

來源、session、頁面有效性、device epoch 與目的 raw 在關鍵階段重驗。來源改寫、目的分頁競爭、切帳號或登出均不能提交成功映射；原來源及衝突版本保留。只合併同 key 且相同款項 ID／操作目標的已知歷史稿；不同固定 ID、未知來源及原請求仍保持阻擋，沒有推測它們已被目前草稿包含。房間與收支在建立新的 pending 前再次檢查原紀錄，防止編輯器打開後才出現的來源被略過。

兩個 IndexedDB 沒有跨庫原子鎖；同源舊頁停寫、後續原請求的明確 adapter、全部未映射來源解決及來源退休後的目的版本查回仍是後續切換條件。

## bot 與驗證

沒有改動既有 schema、outbox、模板、設定語意、bot 入口或 Python／TypeScript worker。共用契約只新增原款項查詢結構，既有帳本提交契約保持。候選正式 web／bot 版本組合尚未成套驗收，不能把本機證據當成正式單邊發布核准。

- strict TypeScript、React／API／bot build 通過；既有前端 bundle 大小警告保持。
- 原稿 decoder／原款項來源、原生收支／結算、活動／身份／管理 bot、投票及 outbox 共 **90 項原生測試通過**。包含十類款項的停用人員篩選、兩種原格式、缺失／重複欄位拒絕、時間歧義、固定目標、全部申報狀態、身份／權限及全資料庫只讀保全；沿用原 Python 差分及 mock Python bot 消費回歸。
- **74 個不同瀏覽器場景已通過**：本批 19 個房間／收支轉換場景，既有財務／結算 18 個，活動／投票轉換及原稿保全 37 個。最後依據／時間顯示調整後，受影響 19 個再次驗證。
- 驗證涵蓋實際表單保存、固定 ID 去重、只讀後續稿、原人員明確移除、strict put／mapping 中止、精確重試、來源與目的衝突、pending 禁止覆寫、目的明確保全、後來的來源阻擋、款項在確認前提交、切帳號與延遲登出。
- 建置後隔離 API、bounded room worker、bot HTTP／WebSocket／ACK／Resume／原生 runtime／SIGTERM、未知投遞與配對備份 smoke 通過；沒有真實 QQ 投遞或正式 worker 操作。
- 360px 轉換預覽及表單操作無水平溢出；人工檢視 `test-results/unified-legacy-money-mobile.png`。測試重跑會清除該合成截圖目錄。
- 初次房間測試誤用已有結算的 fixture，後改用未發布帳單的隔離樣本；人員移除與採用後的測試 locator 改為驗證移除／映射結果。失敗執行不計入通過證據，未停用限流或略過場景。
- 台帳保留全部 166 IDs，維持 `in_progress` 與 `release_eligible=false`。
