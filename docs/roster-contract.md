# P0／P1：逐人報名契約

> 活动阶段、取消结算、安排确认及管理权限以 [P2 活动流程契约](activity-contract.md) 为准。

版本：20261108-3。第一批包含資料結構、遷移、報名及邀請；P2–P6 依完整計畫接續，QQ 登入等待審核。

## 模組與資料

`server.py` 管理 HTTP、身分、權限入口、請求去重；`qgroup_core/storage.py` 管理 SQLite 與版本遷移；`events.py`、`roster.py`、`billing.py` 分別管理活動、參加者及既有人均結算；`audit.py` 管理版本與追加式紀錄。

`users` 是帳號，`browser_sessions` 是瀏覽器憑證；參加者 `attendees` 有獨立 ID、管理人及可空的帳號關聯。代報不建立假帳號，同名不合併。`roster_parties` 的遞增序號固定排隊先後，參加者自己的序號固定組內順序。付款歸屬 `self`／`manager` 僅先記錄責任標記；減免、逐人應付及收退款帳本已由 [P3](settlement-contract.md)／[P4](finance-contract.md) 接續實作。

首次升級在 `BEGIN IMMEDIATE` 內建立遷移版本 1：原瀏覽器憑證複製至新表，舊報名逐筆按原 ID 順序轉為參加者，原正式／候補分配保留。舊 `registrations` 保留並由觸發器禁止再改寫。所有既有結算、人數、圖片、歷史版本均不重算。重複啟動不會重複轉換；失敗整筆回滾。

## 狀態與排隊

| 操作 | 結果 |
| --- | --- |
| 本人／代報，確定參加 | 分配正式或候補；有名額時保留已確認者，依組序填入候補。 |
| 多人一起參加 | 整組分配；空位不足時整組候補並阻擋後方超車。管理人可明確改為分開排隊。 |
| 待確認 | 不占名額、不保留候補優先序；確認時取得新組序，整組模式一併確認。 |
| 後加同行 | 取得新組序，不影響原已確認者；不繼承原報名者優先權。 |
| 正式人員期限前退出 | 標為退出；仍開放報名時依隊列遞補。重新報名排隊尾。 |
| 正式人員期限後退出 | 必填原因，留位等待發起者同意／拒絕；不自動加收費用。 |
| 候補／待確認退出 | 可直接退出，不需發起者審批。 |
| 發起者改動他人報名 | 必填原因；撤銷或審核產生站內消息，並記錄前後資料。 |
| 補報名邀請 | 不占位；受邀者以本人瀏覽器身分接受，額滿須勾選接受候補。已有效報名者不能重複接受。 |

報名關閉／截止後不自動遞補，補人由發起者具理由邀請。截止後邀請接受按當時剩餘名額決定，屬發起者手動補人；原候補不會被默默改為正式。活動手動結束／取消或已有結算時禁止名單異動。

本批沿用舊活動生命週期：依預定時間判斷往期，已取消不能結算。實際結束、延期、現場補錄及取消後帳務在 P2 處理。現有總額結算預設分母改取正式參加者（包括同行），不計候補及待確認；已發布舊帳不變。

## 權限

| 動作 | 可操作人 |
| --- | --- |
| 查看公開活動、名單、歷史、收款碼 | 訪客 |
| 查看邀請活動及其名單、歷史、各版圖片 | 發起者、曾獲授權的瀏覽器帳號 |
| 編輯活動、發邀請、處理退出、填結算 | 發起者 |
| 新增本人／代理報名 | 已填稱呼、可查看活動的瀏覽器帳號 |
| 編輯／退出參加者 | 原管理人；發起者操作他人須原因 |
| 接受個別邀請 | 持該尚未使用連結的瀏覽器帳號；接受前僅可看有限活動概況 |
| 讀取／標記站內消息 | 該消息所屬帳號 |

活動邀請連結可轉傳；取得後由 `/access` 授權目前瀏覽器。個別補報名連結接受後失效。一般訪客、歷史回應不包含邀請憑證或內部帳號 ID；後端日誌遮蔽邀請 token。Cookie 清除或跨裝置的找回仍待 QQ 綁定。

## HTTP 契約

新版請求帶 `X-Kanban-Version: 2`。每次寫入帶 `Idempotency-Key`（16–100 字元英數、底線、短橫線）；相同帳號＋key＋方法／路徑／內容重送回傳首次成功回應，不再次寫入；同 key 換內容回傳 409。瀏覽器遇到逾時／斷線保留原 key，已確定結果才清除。請求結果目前持續保留，沒有自動清除；瀏覽器只保留一天內未確認的 key。

修改既有活動或名單須帶讀取時的 `base_revision`；結算另帶 `base_version`。版本不符回傳 409，須載入最新內容重新確認，不自動重送覆寫。SQLite 將業務、版本、歷史、提醒和去重結果在同一事務提交；歷史失敗則業務一併回滾。沒有實際改動的保存不增加版本。

| 路徑 | 用途 |
| --- | --- |
| `POST /api/events` | 建立活動；發布時自動替發起者報名；網頁不再提供本人參加勾選。API 省略 `join_owner` 預設 true，明確 false 僅保留舊客戶端相容；草稿發布一律自動報名。 |
| `PATCH /api/events/:id` | 編輯或切換狀態；支援 `withdrawal_deadline`、`visibility: public/invitation`，縮小容量不得少於已確認人數。 |
| `POST .../roster/preview` | `{people, intent: registered/tentative, queue_mode: individual/together}` → `base_revision`、`preview_token`、逐人 `allocation`。 |
| `POST .../roster/parties` | 帶原資料與預覽 token；混合正式／候補須 `accept_partial: true`。預覽綁定活動版本及填寫內容。 |
| `PATCH .../attendees/:person` | 修改稱呼／備註／付款歸屬，或 `action: confirm/split`。帳號本人稱呼從個人資料管理。 |
| `DELETE .../attendees/:person` | 退出或提交申請，按需要附 `reason`。 |
| `PATCH .../attendees/:person/withdrawal` | `decision: approve/reject` 與必填原因。 |
| `POST .../roster/invitations` | 發起者提供 `people` 與必填補報名原因。 |
| `GET .../invitations/:token` | 尚有效的受邀概況與目前版本。 |
| `POST .../invitations/:token/accept` | 接受為本人報名；額滿需 `accept_waiting: true`。 |
| `POST .../access` | `{invite_token}` 授予目前瀏覽器查看權限。 |
| `GET .../history?before=:id` | 每頁 50 筆，回傳前後快照、時間、操作者稱呼及原因。 |
| `GET /api/notifications` | 自己最近 100 筆消息及未讀總數。 |
| `POST /api/notifications/read` | `{ids: [...]}` 僅標記自己的消息。 |

`people` 每批 1–20 人；本人 `{is_self:true}`，代理 `{name,note?,payer_kind?:manager/self}`。正式上限 0 表示不限，有限為 1–500。

舊 `/registration` 僅管理帳號本人，不影響同行，並委派同一新服務處理名額、截止、退出與結算鎖定。未宣告 v2 的舊活動／結算接口兼容至 **2026-12-08 UTC**；自 12-09 起回傳要求刷新。新版接口無兼容豁免。

## 發版驗收

先線上備份，將應用放入 root 專用 staging 目錄。以下命令只讀備份、建立全新演練庫，不對正式庫執行：

```sh
python3 deploy/verify_migration.py /path/to/pre-upgrade-backup.sqlite3 /path/to/new-rehearsal.sqlite3
```

檢查舊表逐欄逐值（包含圖片 bytes）、原 Cookie、逐人對照及順序、重跑遷移、外鍵和完整性。正式部署短暫停止舊服務，保留停機當下資料庫快照及舊程式，再替換整套應用，啟動後只讀驗證健康、素材版本和正式資料；最後再備份。任何前端測試僅在本機庫進行。

不能只換回舊程式：舊報名表已鎖為只讀。若新版已有業務寫入，應前向修正；若必須恢復舊庫，先保存新版完整庫並核對新增異動，不能抹掉使用者的新報名或帳款。1Panel／OpenResty 不做任何直接設定修改。
