## 目標與現況

為約 K 群完成從發起、報名、活動變更、現場管理，到費用分攤、收付款與歸檔的完整流程。保持手機優先；一般參加者主要操作仍是報名、管理同行與查看應付，進階選項放在「更多設定」或發起人管理頁。核心模型供未來聚餐、出遊等類別共用。

原有基礎：Python、SQLite、原生 HTML/CSS/JavaScript；Cookie 身分；單帳號單筆報名；正式／候補；活動結束及總額均攤；收款碼、選填備註、不可覆寫的結算歷史；網頁結算版本檢查；每日備份。原有 23 項測試保留，P0／P1 擴充至 50 項。

P0–P2 已拆分帳號與參加者，加入逐人名單、通用異動紀錄、併發保護、預計與實際時間分離、協辦交接、安排重新確認、出席及取消後結算。P3 已完成逐人費用、減免、多人合付及不可覆寫結算版本；P4 已完成收付款、墊付、訂金及結清帳本；P5 已部署本機草稿、未知結果查回、安全重試、待辦、活動複製與導航，手機真機及相容性驗收仍待收尾。

## 一、先固定的設計原則

1. **操作人、參加者、費用承擔人、付款人各自獨立。** 發起人可不參加；代報者可不參加；一位付款人可替多人付款。
2. **名額、出席、分攤各自計算。** 陪同仍占位；候補不收正式參加費；缺席或退出是否負擔費用，依報名時接受的規則決定，不能只從到場狀態推導。
3. **活動、報名開關、帳務狀態分開。** 活動取消後仍可分攤損失或退款；活動結束不等於帳務結清；歸檔不刪除紀錄。
4. **已保存的關鍵異動都可回溯。** 活動條件、名單、角色、減免、分攤、付款歸屬及收退款均記錄操作人、時間、原因與前後內容。尚未送出的表單草稿不是已保存的業務紀錄。
5. **金額用整數分，比例用整數或有理數。** 不使用浮點數計帳；每版應收總額必須與可分攤費用相符。
6. **原資料與舊帳保持原意。** 不根據暱稱自動合併人員，不把新收費規則追溯套用到舊報名，不因新版計算方式重算已發布帳單。
7. **每階段都有手機、權限、競態與資料遷移驗證。** 結算紀錄不提供一般使用者覆寫或刪除接口。

## 二、初始預設規則

這些是第一版實作的預設；可調項在活動設定中公開顯示，會影響費用的規則需保存報名時版本。

| 項目 | 初始行為 |
| --- | --- |
| 發起人是否參加 | 發起表單明確勾選，預設參加；取消勾選即可只組織不占位。舊活動不自動替發起人補報名。 |
| 人數上限／最低成團 | 上限維持不限；最低成團人數選填。未達標提醒發起人決定，不自動取消。 |
| 同行／陪同 | 每位都占名額且預設一份 AA；減免須發起人確認並填原因。 |
| 只代報 | 不自動替操作人報名；被代報者逐人顯示管理人及付款歸屬。 |
| 待確認 | 顯示在待確認清單，不占正式名額、不鎖定候補優先序；轉為正式報名意願時才入隊。 |
| 多人報名 | 提交前顯示分配預覽，明確選擇接受部分候補或必須一起參加。預覽失效時重新確認，不默默改分配。 |
| 必須一起參加 | 整組分配或整組候補；候補按隊列先後，整組排首但名額不足時不自動讓後人超車。介面說明可能暫留空位，可主動改為分開排隊。 |
| 後加同行 | 使用新增時的排隊順序，不繼承原報名者的位置。原已確認成員不因新增同行自動失去名額。 |
| 候補遞補 | 正式報名意願代表願意自動遞補；遞補產生站內提醒。候補可退出；截止後補人改由發起人邀請並由對方確認。 |
| 退出期限 | 與報名截止分開；預設同一時間。期限前可自行退出；期限後可提出退出，費用責任依已公布規則，由發起人處理並留紀錄。未約定的違約費不自動新增。 |
| 遲到／早退 | 約 K 預設不減免，在報名前顯示；個別例外由發起人確認。其他類別可選不同規則。 |
| 時間 | 活動保存自己的時區；新約 K 預設 Asia/Shanghai。跨日顯示完整日期；歷史時間保持原有絕對時間，不猜測未知時區。 |
| 預計結束 | 過了預計結束時間顯示「預計已結束，待確認」，提醒發起人結束或延長；不自動視為實際結束並鎖死安排。 |
| 費用零元／無人分攤 | 零元可發布且無需付款；有正數費用但沒有合法分攤對象時阻止發布。 |
| 減少名額 | 低於已確認人數時阻止直接保存，要求明確處理超額人員；不能靜默降為候補。 |
| 可見性 | 舊活動保持現狀。新活動提供公開／持邀請連結可見；邀請模式的名單、帳務和圖片接口一併驗證權限。建立邀請連結不宣稱能防止轉傳。 |
| 外部訊息 | 必做站內提醒及可複製的變更摘要；QQ 自動群通知取決於另行具備的官方能力，沒有權限時保留人工轉發流程。 |

## 三、狀態與資料模型

實作前先形成狀態轉換表、欄位定義與接口契約，不把所有狀態塞進單一 `events.status`。

| 領域 | 規劃 |
| --- | --- |
| 身分 | 帳號、瀏覽器憑證與外部登入分開；QQ 身分之後綁定到既有帳號。 |
| 活動 | 草稿／未開始／進行中／已結束／已取消；另存報名開關、成團確認、預計及實際時間、歸檔時間。 |
| 活動版本 | 日期、地點、費用規則等版本化；參加者保存接受的版本及待重新確認的變更。 |
| 權限 | 發起人、協辦、一般參加者、代報管理人；列出每個操作的權限矩陣，收退款與轉交權限獨立檢查。 |
| 報名組 | 記錄操作人、同行關係、一起／分開排隊方式與管理權。 |
| 參加者 | 獨立 ID，可未綁帳號；保存稱呼、代報人、正式／候補／待確認／退出，以及獨立的到場狀態。 |
| 排隊 | 保存入隊順序與遞補異動；不依暱稱或現在的名單顯示順序猜測優先權。 |
| 費用 | 費用明細、分攤對象、分攤方式、減免及原因；共同費用與指定人員消費分開。 |
| 結算版本 | 每版凍結人員稱呼、分攤規則、逐人應付、付款歸屬、備註、收款碼及計算明細。 |
| 收付款 | 預收、實收、退款、沖銷與付款分配；參加者「已轉帳」申報與發起人確認的實收分開。 |
| 帳務狀態 | 未發布／收退款中／已結清；改帳後若出現差額，重新進入待處理，保留原收退款。 |
| 稽核／提醒 | 通用追加式異動紀錄與提醒事件；業務寫入與紀錄寫入在同一事務完成。 |

舊結算只有總額及手填人數，未必知道分攤對象。遷移為「舊版人均結算」，保留原金額、除數及所有版本；不得虛構逐人欠款或已付款。轉為新逐人結算時，由發起人核對，產生新版本並保留舊版可查。

## 四、分階段交付

### P0：規則、結構與安全遷移

**交付**

- 整理狀態轉換、權限矩陣、接口契約與上述預設規則。
- 將 HTTP、資料存取、報名規則、結算計算拆為可獨立測試的模組，沿用現有 Python／SQLite 與部署方式。
- 建立帶版本號的資料庫遷移；遷移可重跑、可驗證，明確區分新增欄位與不可逆資料轉換。
- 建立共用異動紀錄、寫入版本檢查、請求去重及重試機制。新寫接口必須校驗版本；舊接口設兼容期限，不能長期繞過新規則。
- 登記既有活動、報名、結算、圖片及歷史的遷移對照，不修改已發布帳單。

**驗收**

- 現有測試及遷移前後資料一致性檢查通過；每個舊結算版本、圖片均可查。
- 使用正式資料的隔離副本演練遷移與恢復；正式資料不作功能測試。
- 重複送出及儲存失敗不造成半筆資料、漏記歷史或重複操作。

### P1：逐人報名、代報與同行

**依賴：P0。**

**交付**

- 本人報名、只代報、增加／取消單位同行，逐人稱呼與付款責任預設。
- 正式、候補、待確認三種意願；一起參加與接受部分候補；提交前名額預覽。
- 名額競態處理、後加同行重新排隊、候補退出及遞補提醒。
- 減少上限時的超額處理，候補轉正時保留原異動紀錄。
- 報名截止與退出期限、退出申請及截止後人工補人流程。
- 活動邀請權限貫穿名單接口；已領取報名不能被其他人只靠稱呼接管。

**手機呈現**

- 普通報名保留一個主按鈕；同行及代報展開後填寫。
- 名單區分正式、候補、待確認，展示每位管理人；本人可單獨管理被授權的同行。

**驗收**

- 代報者不參加時不占位；3 位同行確實計 3 個名額。
- 剩 1 位而提交 3 人、同時搶最後一位、整組候補、後加同行均按規則分配。
- 只能管理本人或受託名單；修改、退出及遞補均留紀錄。

### P2：活動生命週期、變更與現場管理

**依賴：P1。**

**交付**

- 草稿、成團條件、報名開關及活動進行狀態；預計／實際結束分開。
- 跨日日期、活動時區、提前結束、延長活動、臨時換地點。
- 重要變更摘要、站內提醒、已讀與重新確認；未重新確認的人明確標記，不直接當成退出或無條件接受。
- 涉及新費用責任的變更需明確接受；拒絕或未接受者的處理保留原約定，不追溯加收。
- 發起人轉交、協辦權限及操作紀錄；轉交需對方接受，不能憑空把責任交給他人。
- 到場、缺席、遲到、早退、臨時加入的現場核對，與費用責任分開。
- 取消原因與可追溯歸檔；允許取消活動保留結算入口。已有帳務時不提供抹除紀錄的移除方式。
- 活動關鍵條件版本化，不允許舊分頁覆蓋新安排。

**驗收**

- 通宵活動顯示正確日期；超過預計結束仍能確認延長，不會無故鎖死。
- 改日期／地點／收費規則後，每位參加者的確認狀態清楚可見。
- 最低人數未達標只提醒；取消後仍可處理訂金損失與退款。
- 非授權協辦不能轉交活動或管理帳款；所有現場補錄可回溯。

### P3：逐人費用與結算版本

**依賴：P2。**

**交付**

- 費用明細與消費憑證圖片；區分共同消費、指定人員消費、退款和減免。
- 按人均分、按份數／比例、固定指定金額；再加入按參與時長分攤，可組合不同費用項目。
- 同行預設正常 AA；免 A、半 A 等由發起人確認，保存原因。
- 結算前核對名單；按已接受的退出／缺席規則保留或免除相關費用責任。
- 每人應付、每位付款人合計與明細，支援代付及多人合付。
- 整數分計算；尾差採固定、可解釋的分配順序，每個費用項目的分配合計精確等於該項金額。
- 完整結算快照與差異展示；名單、費用、備註、收款碼和付款歸屬的修改均產生版本。
- 舊人均帳單保持唯讀原貌；轉新版需核對後新增版本，不自動重算舊帳。

**驗收**

- 5 位本人加 2 位同行共占 7 位，其中 1 位免 A，600 元共同費用除以 6 份，每份 100 元。
- 免 A 者仍可分擔其指定的個人消費；不同費用項目可有不同分攤範圍。
- 全員免 A 但存在正數費用時阻止發布；0 元結算可發布。
- 缺席者按原約定處理；不因勾選缺席就直接免除費用。
- 改暱稱、同行關係或付款人，不改寫已保存的舊版本；併發編輯不互相覆蓋。

### P4：預收、墊付、實收與退款帳本

**依賴：P3。**

**交付**

- 參加者申報已轉帳，發起人確認實收；支持現金、代付、部分支付、多付與重複付款。
- 每筆款項保存金額、付款人、收款人、歸屬與時間；錯記採沖銷／更正，不刪除原款項。
- 預收參加費是付款抵扣；發起人或其他人墊付是支付費用與報銷關係，不能當作降低活動消費總額。
- 已計入最終店家帳單的訂金不重複計費；可退押金單獨追蹤，只有實際損失才轉費用。
- 店家退款、活動取消損失、已收款退回及墊付報銷，明確顯示資金流向。
- 改帳後保留實收，逐付款人顯示補款／退款；付款歸屬調整需明確處理原分配，不默默轉移已確認款項。
- 收退款中／已結清；全部費用、收退款與報銷對平才可結清。結清後更正生成新版本，出現差額時重新待處理。

**驗收**

- 預付、代付、少付、多付、重複申報、重複確認和退款重試不重複入帳。
- 已付 100 元、改帳後應付 120 元時顯示補 20 元；改成 80 元時顯示應退 20 元。
- 活動取消後可以只結算訂金損失並退還餘款；活動取消不代表帳務結清。
- 付款申報不能直接變成已收款；只有合法權限能確認或沖銷款項。

### P5：完整手機體驗、提醒與日常使用

**依賴：依 P1–P4 逐步交付，最後集中驗收。**

**交付**

- 分角色呈現「我的報名／同行」「現場名單」「我的應付／補退款」「發起人管理」，保持首頁卡片精簡。
- 活動與結算草稿、關閉未保存提示、刷新恢復；草稿按帳號及活動隔離，退出身分或改用其他帳號時不混用。
- 行動網路逾時與失敗重試；送出結果未知時先查操作結果，建立活動與財務操作可安全重試。
- 站內未讀提醒與待辦：遞補、活動重要變更、重新確認、成團決定、結束確認、補退款及未結清。
- 提供可複製的活動／變更摘要供人工轉發，不假設已通知整個 QQ 群。
- QQ 內置瀏覽器的剪貼簿退路、收款碼查看／保存原圖、圖片失敗與上傳重試。
- 常用活動複製、類別預設、集合地點與導航入口；只複製安排，不複製名單、付款、收款碼或歷史。
- 長名單、長標題、大字體、軟鍵盤、返回鍵、表單焦點、空資料及錯誤頁檢查。
- 公開／邀請模式下，列表、分享、圖片、歷史、憑證與直接接口存取的完整權限測試。

**驗收**

- 360px 窄螢幕及常見手機尺寸可完成整個流程，底部操作不被鍵盤或提示遮住。
- 重整、斷線、返回上一頁與重複點擊不丟草稿、不重複報名、不重複收款。
- 使用真實手機的 QQ 內置瀏覽器確認圖片與分享行為；無法自動識別收款碼時有可用退路。
- 未授權訪問者無法從圖片直連或歷史接口繞過活動可見性。

P5 功能已於 2026-11-08 部署 20261108-7，360px 與桌面瀏覽器驗收通過，詳見 [日常恢復契約](experience-contract.md) 與 [發布紀錄](releases/2026-11-08-experience.md)。本版已補長標題、25 人名單與兩倍字體的 360px 排版驗收及修正。真實手機 QQ WebView、系統鍵盤、長按／保存圖片與系統大字體仍待使用者實機確認；不列為已通過。QQ OAuth 不在本階段啟用。

### P6：QQ 身分接入與獨立的認領／裝置授權

**QQ 登入、回調與帳號綁定已於 20261109-qq1 實作，官方審核及真實 QQ 授權待驗證。代報認領、明確帳號衝突處理及裝置授權已獨立完成，不依賴 QQ。**

**交付**

- QQ OAuth 登入、回調驗證、既有瀏覽器帳號的明確綁定，以及跨裝置取回管理權。
- 對帳號衝突設可預覽的處理流程；不按暱稱自動合併，不靜默轉走活動或付款責任。
- 被代報者透過受控邀請或管理人確認認領報名；已自行報名者處理重複項，保留原排隊與帳務紀錄。
- QQ 登入與群資格分開；按實際可用能力選擇邀請／管理人審核，不宣稱 OAuth 能證明群成員身分。
- 若另具備官方群通知能力，再接入外部通知；訊息去重、失敗可重試，不能因發送失敗回滾已成功的報名或收款。

**驗收**

- 綁定前建立的活動、報名與帳務仍可管理；另一裝置登入同一帳號可找回。
- 認領同一人不會多占名額、多算 AA，既有收款和歷史歸屬保持可查。
- 同名不同 QQ 帳號不合併；重放回調、失效邀請和越權認領均被拒絕。

## 五、全流程驗收案例

除各階段測試外，至少跑通以下完整場景：

1. 發起人不參加，代報兩人，其中一人後來自行登入並認領；名額及金額不重複。
2. 剩一個名額時多人同行報名；正式／候補清楚，退出後正確遞補，整組與分開模式都符合排隊規則。
3. 報名後改日期與費用；有人接受、有人拒絕、有人未確認，名額與費用按原／新約定處理。
4. 通宵活動臨時延長；有人遲到、早退、未到，另有人現場加入，最終分攤可解釋。
5. 共同行程中，部分人喝酒、部分人免共同費用、有人半份 AA；各費用項目合計與逐人應收精確對平。
6. 活動已預收款但臨時取消；訂金部分損失、押金退回，完成應收損失、退款與墊付報銷。
7. 部分人已付款後修改總額、名單、減免或付款歸屬；保留原收款，正確計算補退款。
8. 兩位管理者同時改名額或帳單，手機斷線後重試；不超賣、不漏紀錄、不重複入帳。
9. 發起人臨時缺席、轉交管理；協辦只能操作授權範圍，完整保存交接與帳務歷史。
10. 歸檔後發現錯帳；原版本仍可查，更正產生新版本並重新處理差額。
11. 未授權者拿到普通活動 ID 或圖片地址，仍不能繞過邀請模式的權限。
12. 使用備份還原到隔離環境，名單、各版圖片、應收、實收及退款能對平。

## 六、發版與資料保全

- 每階段在本地測試庫完成，再使用正式庫的隔離副本驗證遷移；不新增測試報名或測試款項到正式活動。
- 新模型與接口先完成兼容層，前端切換後再移除舊接口；不得讓舊接口繞過新名額、權限或帳務規則。
- 每次發布前備份程式及 SQLite；檢查筆數、金額、圖片摘要、歷史與外鍵完整性；發布後核對健康檢查及公開／受限接口。
- 程式回滾與資料回滾分開評估。發布後若已有新寫入，不直接還原舊資料庫抹掉新增報名或款項；優先前向修復，必要時在維護窗口做可對帳的恢復。
- 保持 server2 現有服務和連接埠；1Panel 的網站、代理與 TLS 繼續由面板標準流程管理，不手寫代理設定。
- 發版紀錄寫清已交付功能、預設規則、兼容範圍及未完成項；每一階段都能獨立驗收。
